## 1. ① 액션 경유 전환 — 핸들러 자체를 옮긴 것이 핵심

인계는 "`_unhandled_key_input` 의 키코드 판정을 액션 청취로 전환"이었으나, **그 자리에 두면 전환해도 효과가 없다**:

> `_unhandled_key_input` 은 `InputEventKey` 만 받는다. 액션으로 바꿔도 **패드 이벤트가 애초에 그 함수에 도달하지 못한다.**

그래서 두 조작을 **`_unhandled_input` 으로 옮겨** 결선했다. 남은 레이스 전속 조작(리스핀 R · 차지 개입 C · 홀드 1/2/3)은 키 경로에 그대로 뒀다 — 패드 열이 조합 입력(`X + D패드 좌우 → A` 등)이라 별도 배정 대상이다.

**키보드 거동 보존이 계약이었고, 지켰다.** 액션이 매핑표의 키보드 열을 이미 담고 있어(IMPL-186) 전환은 동작 집합을 **넓히기만** 한다. 검사로 3경로를 각각 확인했다:

| 조작 | 키보드 | 패드 | 액션 |
|---|---|---|---|
| 스핀 커밋 | Space ✅ | Button 0 (A) ✅ | `ui_accept` ✅ |
| 일시정지 | Escape ✅ | Button 6 (Start) ✅ | `pause_menu` ✅ |

> **봉인 준수:** 스핀 검사는 **결과를 보지 않는다** — 국면이 T1 을 벗어났는지만 본다(불변규칙 5).

**설계 의도 보존 확인.** "확정 = 스핀과 같은 물리 동작으로 순환"(D09 §1.3 주석)은 불변이며, 오히려 패드에서도 **A 하나로 같은 순환**이 성립하게 됐다. 바뀐 것은 입력 판독 층뿐이다.

> **부수 이득 1건.** 두 핸들러의 키 집합이 **disjoint** 가 되어(공통 층 = `_unhandled_input` / 레이스 층 = `_unhandled_key_input`) 엔진의 호출 순서에 의존하지 않는 구조가 됐다. 어느 쪽이 먼저 불려도 이중 발화가 없다.

## 2. ② 탭 순회

3화면 모두 **액션 청취를 추가**했다 — `button.pressed` 경로는 손대지 않아 마우스·포커스 조작이 불변이다.

| 화면 | 탭 | 순회 축 |
|---|---|---|
| `options_screen` | 5 | `_active_tab` 인덱스 |
| `achievement_screen` | 5 | `_active_tab` 인덱스 |
| `records_screen` | 3 | `_tabs` **삽입 순서 = 화면 탭 배치 순서** |

`records_screen` 에 별도 순서 배열을 두지 않은 것은 의도다 — 두면 배치와 갈릴 수 있고, 갈린 순간 "패드로는 다른 순서로 돈다"가 된다.

> **[가안] 경계에서 감긴다(wrap).** D09 는 순환 방향·경계에 침묵한다. 탭이 3~5개로 적어 끝에서 막히면 반대 방향 키를 다시 찾아야 하므로 감는 편이 조작 비용이 낮다고 봤다.

**회귀에 패널 가시성을 함께 넣었다** — 인덱스만 바뀌고 화면이 안 따라오는 결함이 실재할 수 있는 형태라, `_active_tab` 단언만으로는 부족하다.

## 3. ③ 툴팁 고정 — 배치 지점이 설계 요점

포커스 대상의 `tooltip_text` 를 **코드 생성 오버레이 1장**으로 띄운다. 신규 화면·라우트·씬 0.

### `FlowScreen._shortcut_input` 에 둔 이유

베이스에 `_unhandled_input` 으로 두면 **정의한 화면에서만 조용히 죽는다.** GDScript 는 자동 super 호출이 없어서, 이미 `_unhandled_input` 을 가진 화면(옵션·업적·기록실·레이스)이 베이스 구현을 통째로 가린다. "전 화면 공통 기구인데 일부에서만 안 먹는" 형태가 되고, 그건 눈으로 알기 어렵다. `_shortcut_input` 은 아무 화면도 쓰지 않는 층이라 상속이 성립한다.

### 검사 층 정합

- **PAL 무접촉** — 색은 `UiPalette.BG_PANEL`·`FRAME_LINE`·`TEXT_PRIMARY` 상수 경유(리터럴 0)
- **FONT 준수** — `_body_font_size` 창구 경유. 돌연변이로 이 한 줄을 빼자 **실제로 16 으로 렌더**됨을 확인했다(§5 M5)

### [가안] 3건 (D09 침묵분 — impl_log 등재)

| # | 규격 | 근거 |
|---|---|---|
| 1 | 위치 = 화면 하단 중앙 | 포커스 대상 옆에 붙이면 정작 그 대상을 가린다 |
| 2 | 해제 = 재입력 · 포커스 이동 · 화면 이탈 | 포커스가 옮겨가면 내용이 어긋난다 |
| 3 | **빈 툴팁이면 상자 자체를 안 띄운다** | 빈 상자는 "정보가 있는데 못 읽는" 오해를 준다 |

실기 판독(위치·가독)은 주력 후속이다.

## 4. ④ 홀드 감광 — **비의도 판정**

`Color(0.75, 0.78, 0.82)` → **`Color(0.78, 0.78, 0.78)`**.

**조사 결과 근거 부재:**
- git 이력 — RACE-01 초판 커밋 `2fef8e9` 에서 처음 들어왔고, 커밋 메시지·주석에 채널 불균등의 언급이 없다
- 설계 — D09 §3.2 는 홀드의 **이중 표시**(프레임 잠금 + 토글 점등)만 규정하고 **감광 자체를 규정하지 않는다.** 한색 편이의 근거는 어디에도 없다

인계 §4 "근거 없으면 비의도"에 따라 정규화했다. **감광은 상태 표시이지 색 정보가 아니므로**, 색상 이동은 심볼 판독(D10 §5.1 색+도상 이중 부호화)에 잡음이 된다. 감광률은 구 값의 **중앙 채널(0.78)** 을 취해 실화면 인상을 보존했다 — 눈 대조는 주력 후속.

## 5. 반증 — 돌연변이 7건 전건 검출

| # | 돌연변이 | 검출 |
|---|---|---|
| M1 | `ui_accept` → 원시 키코드 직독 복귀 (패드 무반응 재발) | `[FAIL] 액션 — 스핀 커밋 도달 phase=0` |
| M2 | `pause_menu` → 원시 키코드 직독 복귀 | `[FAIL] 액션 — 일시정지 열림` |
| M3 | 탭 순회 감김 제거 (경계 clamp) | `[FAIL] 경계에서 감긴다(wrap) active=0` |
| M4 | `tab_prev` 청취 제거 | `[FAIL] tab_prev 로 되돌아온다` |
| M5 | 툴팁 고정 폰트 창구 우회 | `[FAIL] D13 폰트 크기 보유 — **actual=16**` |
| M6 | 빈 툴팁에도 상자 표출 | `[FAIL] 툴팁 고정 표출` |
| M7 | 홀드 감광 한색 편이 복귀 | `[FAIL] 등채널 — (0.75, 0.78, 0.82, 1.0)` |

> **M5 가 FONT 신설 근거를 실증한다** — 창구를 한 줄 빼자 코드 생성 라벨이 **엔진 기본 16** 으로 떨어졌다. 640×360 캔버스에서 그 크기는 레이아웃을 깨뜨리고, 화면은 정상적으로 뜨므로 눈으로는 "글자가 좀 크네" 정도로 보인다.
