## 1. ① 패드 입력맵 — 집행분과 **인계 문면과의 차이 2건**

### 집행 결과 (전건 재실측 확인)

| D09 §1.3 행 | 액션 | 키보드 | 패드 |
|---|---|---|---|
| 확인 / 선택 | `ui_accept` | Enter · KpEnter · Space | **Button 0 (A)** |
| 취소 / 뒤로 | `ui_cancel` | Escape | Button 1 (B) — IMPL-178 |
| 탭 전환 | **`tab_prev`** / **`tab_next`** | Q / E | **Button 9 (LB)** / **Button 10 (RB)** |
| 일시정지 메뉴 | **`pause_menu`** | Escape | **Button 6 (Start)** |
| 상세 정보 | **`detail_info`** | T | **Button 3 (Y)** |
| 포커스 이동 | `ui_up/down/left/right` | 방향키 | D패드 11~14 + 좌스틱 축 (§1-나) |

버튼 인덱스는 **짐작하지 않고 엔진에서 실측**했다 — A=0 · B=1 · Y=3 · Start=6 · LB=9 · RB=10 · D패드 11~14 · 좌스틱 = 축 0/1.

### 가. **신설 액션은 3종이 아니라 4종이다**

인계 §1 은 "신설 3액션"이라 했으나, '탭 전환' 1행이 매핑표에서 **Q·E / LB·RB** 즉 **방향 2종**이다. 방향이 있는 조작은 액션 1개로 표현할 수 없다(어느 방향으로 넘길지가 사라진다). **행 3 = 액션 4** 로 집행했다 — "3종"은 행 수를 센 것으로 읽었다.

### 나. **`ui_up/down/left/right` 는 손대지 않았다 — 4차 회신 과잉 보고 정정**

인계 §1 은 "방향 4행에 D패드 + 좌스틱 축 추가"를 지시했으나, **엔진 기본이 이미 담고 있음을 실측**했다:

```
ui_up    :: Up   / Joypad Button 11 (D-pad Up)    / Axis 1 Value -1.00
ui_down  :: Down / Joypad Button 12 (D-pad Down)  / Axis 1 Value  1.00
ui_left  :: Left / Joypad Button 13 (D-pad Left)  / Axis 0 Value -1.00
ui_right :: Right/ Joypad Button 14 (D-pad Right) / Axis 0 Value  1.00
```

> **정정.** 4차 회신 §2 에서 방향 4행을 "바인딩 부재"로 보고한 것은 **잘못이다.** 그때 실측한 것은 `ui_cancel`·`ui_accept` 둘뿐이었고 방향 4행은 "`[input]` 섹션이 없으니 없겠지"로 추정해 표에 넣었다. 이번 인계 §1 이 그 오보를 근거로 작성됐으므로 먼저 바로잡는다.

**그래서 적지 않았다.** `[input]` 에 액션을 적으면 엔진 기본 이벤트를 **대체**하므로, 이미 완전한 4행을 손으로 다시 적는 것은 이득 없이 **부분 전사로 잃을 위험만** 만든다. 계약의 고정은 아래 회귀 검사가 맡는다. (같은 이유로 새로 적은 액션들은 매핑표의 키보드 열을 함께 담았다 — 패드만 적으면 키보드가 조용히 죽는다.)

### 회귀 축 — UISCR 입력맵 계약 (20검사)

| 축 | 내용 |
|---|---|
| 액션 실재 + 패드 버튼 인덱스 | 10액션 각각. **`as_text` 가 아니라 인덱스로 단언** — 표기 문구는 엔진 판올림에 흔들린다 |
| 좌스틱 축 | 방향 4행에 `InputEventJoypadMotion` 존재 |
| **키보드 열 보존** | 신설·수정 6액션. `[input]` 의 대체 성질 때문에 **조용히 키보드가 죽는 경로가 실재**한다 |

리매핑 탭(§6.4)이 나중에 기본값을 바꿔도 **"액션 자체의 존재"는 불변 계약**이라는 것이 이 검사의 취지다.

### 신설 액션 3종의 **소비부 실태 조사** (결선 없음 — 보고만)

| 액션 | 현재 소비부 | 실태 |
|---|---|---|
| `tab_prev` / `tab_next` | **없음** | 탭 보유 화면 3종(`options_screen` 5탭 · `achievement_screen` 5탭 · `records_screen` 3탭)이 전부 **`button.pressed` 전속**이다. 탭을 바꾸려면 탭 버튼까지 포커스를 옮겨야 한다 |
| `pause_menu` | **있으나 액션을 안 듣는다** | `race_screen.gd:255` 가 `key.keycode == KEY_ESCAPE` 로 **원시 키코드 직독**이다. 액션 경유가 아니므로 **패드 Start 는 여전히 안 먹는다** |
| `detail_info` | **없음** | 툴팁 고정 기구 자체가 미구현. 현재 툴팁은 엔진 기본 호버(`tooltip_text`) 전속이라 패드로는 띄울 방법이 없다 |

> **⚠ 조사 중 추가 발견 — `ui_accept` 도 RACE-01 에서는 안 먹는다.** 같은 `_unhandled_key_input` 이 `KEY_SPACE`·`KEY_ENTER`·`KEY_KP_ENTER` 를 **원시 키코드로 직독**한다(`race_screen.gd:262`). 즉 **액션은 생겼지만 레이스 화면의 주 행동(스핀·확정)은 패드 A 에 반응하지 않는다.** D09 §1.2 "패드 풀 지원 — 전 기능, 마우스 병용 불요"에 직접 걸리는 지점이라, 소비부 배정 시 **원시 키코드 직독 → 액션 경유 전환**을 같은 묶음으로 보는 편이 안전하다. (이번 몫이 입력맵 전속이라 손대지 않았다.)

## 2. ② PAL 문맥 제외 2축

### 구현

| 축 | 판정식 | 근거 |
|---|---|---|
| ① 프로퍼티 문맥 | 줄에 `modulate` 포함 | 씬 `modulate =` · 코드 `.modulate =` · 트윈 `"modulate"` 인자를 모두 덮는다. **줄 단위로 좁힌 것은 의도** — 한 줄이 게인과 도색을 함께 쓰는 형태는 실측상 부재하고, 표현식 파싱까지 가면 검사가 스스로 오검출원이 된다 |
| ② 순 무채 + 알파 | R=G=B **정확히 일치** 이고 알파 < 1 | 스크림·완전 투명. 무채 조건을 좁게 걸어 **감광 층으로 위장한 도색**이 새지 않게 했다 |

**제외를 허용 목록으로 처리하지 않았다** (인계 §2 지시 이행). 허용 목록은 "대장 밖이지만 이 건은 봐준다"는 **판단 기록**이고, 이 둘은 "애초에 검사 대상이 아니다"라는 **검사 정의**다. 섞으면 목록이 판단인지 정의인지 알 수 없게 된다. 사유는 검사 주석에 명문화했다.

### 재계수 — **181 → 174**

| 축 | 이전 | 이후 |
|---|---|---|
| 총 경고 | 181 | **174** (−7) |
| `.tscn` | 177 | **174** |
| `.gd` | 4 | **0** — `.gd` 위반은 **전부** 게인·스크림이었다 |
| 고유 색 종수 | 24 | **17** |

**제외된 7건의 정체:**

| 색 | 축 |
|---|---|
| `Color(1.6, 1.6, 1.6)` | ① 게인 (트윈 `modulate`) |
| `Color(1.0, 1.0, 1.0)` · `Color(0.75, 0.78, 0.82)` | ① 릴 홀드 틴트 (`.modulate =`) |
| `Color(0, 0, 0, 0.55)` · `Color(0.0, 0.0, 0.0, 0.55)` · `Color(0, 0, 0, 0.45)` | ② 모달 스크림 |
| `Color(1, 1, 1, 0)` | ② 완전 투명 |

> **유채+알파는 잔존한다 — `Color(0.04, 0.05, 0.06, 0.72)` ×4 확인** (인계 §2 명문 이행).

**남은 174건의 성격은 4차 보고와 동일**하다 — 상위 5종 150건이 구 팔레트 값(구 `TEXT_PRIMARY` 61 · 구 `TEXT_DIM` 40 · 구 `BG_DEEP` 26 · 구 `FRAME_LINE` 15 · 구 `BG_PANEL` 8)이며 기계 치환이 성립한다. 파일별 상위 = `race_screen.tscn` 57 · `tour_report_screen.tscn` 15 · `gp_result_screen.tscn` 14 · `repair_bay_screen.tscn` 10.

### 반증

**(가) 문맥 probe 7건 — 전건 기대 일치**

| 주입 | 기대 | 결과 |
|---|---|---|
| 유채 + 알파 도색 `Color(0.04,0.05,0.06,0.72)` | 경고 | ✅ 경고 |
| 순 무채 + 알파 `Color(0.0,0.0,0.0,0.55)` | 제외 | ✅ 제외 |
| 순 무채 + 알파 0 `Color(1,1,1,0)` | 제외 | ✅ 제외 |
| **무채이나 알파 1** `Color(0.5,0.5,0.5,1)` | 경고 | ✅ 경고 |
| `modulate` 문맥 게인 `Color(1.6,1.6,1.6)` | 제외 | ✅ 제외 |
| `modulate` 문맥 틴트 `Color(0.75,0.78,0.82)` | 제외 | ✅ 제외 |
| **비-modulate 문맥의 같은 색** (음성 대조) | 경고 | ✅ 경고 |

**(나) 제외 축 무력화 돌연변이 3건 — 전건 검출**

각 돌연변이마다 "정상 검사에서는 그 probe 가 잡히는가"를 **먼저 단언**하고(탐지 가능성 확인), 그다음 돌연변이에서 누락되는지를 봤다.

| 돌연변이 | probe | 정상 → 돌연변이 |
|---|---|---|
| 무채 조건 완화 (`\|R−B\| ≤ 8`) | 유채+알파 도색 | 검출 → **누락** |
| 알파 조건 제거 | 무채 + 알파 1 도색 | 검출 → **누락** |
| `modulate` 제외를 전면 제외로 | 임의 도색 `#123456` | 검출 → **누락** |

세 축이 전부 "느슨해지면 도색이 샌다"를 실증한다 — 특히 첫째는 인계 §2 가 경고한 실패 모드 그 자체다.
