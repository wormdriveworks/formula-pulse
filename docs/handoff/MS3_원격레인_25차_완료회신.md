## 1. [1순위·차단급] 저장 격리 훅

### 1.1 설계의 핵 = **기본값을 두지 않았다**

| 안 | 결과 |
|---|---|
| 기본 = `user://` (편한 쪽) | **지금의 사고** — 훅을 안 부른 하네스가 실 프로필을 지운다 |
| 기본 = 테스트 루트 (안전한 쪽) | **실기가 망가진다** — 플레이어 세이브가 격리 폴더로 간다 |
| **기본 없음** | 미설정 = 경로 없음 → 저장·로드가 **소리내어 실패** |

세 번째를 택했다. 이 파일이 프로필 개수에 **이미 쓰고 있는 방식**이다 —
*"미설정 상태의 저장·로드는 실패하게 해 우회를 소리나게 만든다"*(기존 주석). 같은 근거를 루트에 연장했다.

```
LIVE_ROOT "user://"          ← app_root._ready() 한 곳만 주장
TEST_ROOT "user://test_profiles/"  ← 하네스 전량
_root 기본 ""                ← 미설정이면 push_error + 빈 경로
```

### 1.2 **실기 루트가 격리 루트를 덮었다** — 훅을 만든 뒤에 발견

훅을 넣고 게이트를 돌렸더니 **바이트 대조가 여전히 붉었다**(`profile_2` 재변조).
원인: UISCR 이 `app_root.tscn` 을 **실제로 세우는 축**이 있고 그 `_ready()` 가
격리 루트를 실기로 되돌렸다. 그 뒤 스위트의 저장이 전부 실 프로필로 갔다.

교정 = `use_live_root()` 이 **이미 잡힌 루트에 양보**한다. 앱은 *아무도 잡지 않았을 때만* 실기를 주장한다.

> **이것이 밖의 방어가 필요한 이유의 실증이다.** 훅·전수 검사(안쪽)는 전부 녹색이었고
> **실 파일 바이트만 달랐다.** 소스 검사는 *언제 효과가 나는지*를 보지 못한다.

### 1.3 세 겹

| 겹 | 위치 | 보는 것 |
|---|---|---|
| 안 | `SaveManager` 기본값 부재 + 미설정 경고 | 우회가 조용해지지 않는가 |
| 중 | **UISCR ㉑** — 세이브 접촉 하네스 전수(24개) × 훅 경유 계수 · 하네스의 실기 루트 호출 0 · 앱 부팅 거동 | 새 스위트가 추가될 때 먼저 걸린다 |
| **밖** | `run_tests.sh` 게이트 전후 **실 저장 파일 md5 대조** | **피해 자체** — 훅을 우회하는 새 경로가 생기면 여기만 붉어진다 |

### 1.4 총괄 증보 — **백업까지 함께 덮이는 경로**

내러티브 7차가 `progress.json` 과 `progress.bak.json` 이 **함께** 덮인 것을 실측했다 —
1차와 복구가 동시에 소진되면 가드는 탐지만 하고 되돌릴 것이 없다. 축으로 넣었다:
진행·백업·스냅숏 **세 경로 전부**가 격리 루트 안이고 서로 다르다는 것을 값으로 확인한다.

`options.json` 도 같은 루트를 탄다 — 21차에 내가 실 옵션 파일을 쓴 축이 있었고 그것도 같은 사고였다.

## 2. 좁은 슬롯 정밀 배정 — 그리고 **방법 교정 1건**

11슬롯 정밀 배정(6 → 11). 그런데 배정하면서 **초판의 방법이 틀렸다는 것이 드러났다.**

### 2.1 `custom_minimum_size` 는 하한이지 상한이 아니다

23·25차 초판은 이 값을 슬롯 폭으로 읽고 초과를 **판정**했다. Godot 의 `custom_minimum_size` 는
라벨이 **그보다 작아지지 않게** 하는 값이고 텍스트가 넓으면 라벨이 커진다 —
**컨테이너가 자르지 않는 한 절단은 없다.**

실측이 그것을 드러냈다: `ui.achievement.markPending`(en) `Not Earned` = **49px vs 선언 44px** 인데
소비 노드는 `HBoxContainer` 안이라 **행이 넓어질 뿐 잘리지 않는다.**

그래서 이 계열을 **판정에서 관측(①-c)으로 내렸다.** 진짜 구속은 *행 총폭 대 컨테이너 폭*이고
그것은 ①-b(선택지 행)처럼 행 구성이 알려진 자리에서만 기계로 셀 수 있다.
초과는 **보고**한다 — 설계 폭을 넘는다는 사실은 레이아웃 밀림의 단서이고 판정은 화면 층 실기 몫이다.

**느슨한 판정으로 통과시키는 것보다, 정직한 관측이 낫다.**

### 2.2 랩 대장 폭 2건 교정
초판이 어림한 300 을 실 선언값으로 고쳤다 — 콜아웃 **220** · 확인 패널 **240**.
랩 판정은 폭에 직접 반응하므로 어림한 폭은 줄 수를 **과소 계상**한다(J9 검출: 240 → 40 주입 시 5줄 적출).

### 2.3 현황
`①` 판정 = 실 rect 슬롯 3(로그 255·VN 본문 620·선택지 행 640) + 파싱 슬롯 2 · `①-c` 관측 7계열 ·
`②` 랩 3계열 · `③` 기본 상한 · **초과 판정 0 · 선언 폭 초과 관측 1건**(§2.1).

## 6. ② 스킬 문면 8키 결선을 차기로 넘긴다 (판단·근거)

`warnings=8` 은 전량 그 키들의 V6 고아이며, 결선은 `race_screen` 의 슬롯 UI 층이다
(주력 13차가 방금 세운 화면). 넘기는 근거 셋:

1. **이 회차는 차단급 하나로 이미 무겁다** — 저장 격리는 안·중·밖 세 겹 + 실기 루트 누출 교정까지 왔고, 그 위에 화면 층 결선을 얹으면 회귀 표면이 두 축으로 갈린다.
2. **거부 분기가 19종으로 늘었다** — 총괄 증보가 지적한 대로 리터럴 15 + `_skill_precondition` 경유 4이며 `sector_turn` 누락 주의가 붙어 있다. 문면 5키로 19분기를 덮는 **매핑 설계**가 먼저 필요하고, 그 설계에는 ③의 2키(즉납 예정)와 ④의 침묵 3종이 입력으로 들어간다 — **키가 다 모인 뒤 한 번에 하는 것이 맞다.**
3. **거부 고지 슬롯이 주력 몫으로 분리됐다**(총괄 명문 · 최소 100px). 표시 자리가 서기 전에 매핑만 넣으면 소비부 없는 문면이 또 생긴다.

차기 회차 입력을 이 회신에 남긴다: 침묵 3종 대장(`SEAL_SILENT_ERRORS`) · `already` 2분할 · error 코드 전량(20차 §1.1) · 요청 2키.
