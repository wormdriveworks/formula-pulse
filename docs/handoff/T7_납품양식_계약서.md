## 1. 이벤트 스키마

**예시 행 (기존 데이터 인용 — `events.csv:2`)**

**[집필] 납품 양식**

```csv

```

> **`scope=stage` 는 그 무대의 `event_pool` 에 id 가 들어가야 후보가 된다** — 무대 구조 JSON(`stage_*.json`)의 `event_pool` 배열이 실제 소비 지점이다(`event_service.gd:69` `_candidates()`). 열만 `stage` 로 두고 풀에 안 넣으면 **영원히 안 뽑힌다.**

### 1.2 [현행] `godot/data/structures/event_variants.json` — 변형 4축

```json
"event_rank_friction": [
  {
    "tag": "jude_adjacent",
    "text_key": "ui.eventVariant.rankFrictionJudeAdjacent",
    "condition": {"all": [{"field": "jude_rank_delta", "op": "<=", "value": 2}]}
  },
  {
    "tag": "default",
    "text_key": "ui.eventVariant.rankFrictionDefault",
    "condition": {}
  }
]
```

**계약 3건**
1. **평가는 배열 순서대로 첫 매치 1건**(`_select_variant()`). `default` 는 **반드시 마지막**에 둔다.
2. **`condition: {}` = 조건 없음 = 항상 성립.** 폴백 행은 이 형태다.
3. 폴백이 없으면 조건 전건 불성립 시 `text_key` 가 **빈 문자열**로 나간다 — 화면에 아무 문면도 안 뜬다.

### 1.4 [현행 부재] 앵커 필드 — D12 §5.4 구속이 데이터에 아직 없다

D12 §5.4 는 `anchor_type ∈ {milestone_act, stage, tour_slot}` + `tour_slot ∈ {1,5}` 를 **확정 구속**으로 두었고 V5 가 그것을 차단형으로 지킨다. **그런데 `events.csv` 에는 그 열이 없다** — V5 는 열이 있는 행만 보므로(`run_validators.gd:913` `if row.has(slot_field)`) 현재 이벤트는 V5 검사 대상이 아니다.

현행 유일한 앵커 보유 실물 = `godot/data/structures/scripted_loss_s1.json` (`"anchor_type": "tour_slot"`).

**[신설안 A — 승인 대기]** 이벤트에 앵커 결속을 부여할 경우 `events.csv` 에 `anchor_type`·`tour_slot` 2열 추가. **집필이 앵커를 요구하는 이벤트를 납품하면 이 신설안이 함께 발효되어야 한다** — 총괄 판정 사안이며 구현이 임의로 열을 만들지 않는다.

### 1.5 [신설안 B — 승인 대기] `tone` 열

**문제.** VN 트랙 2종(BGM-09 일상 / BGM-10 긴장)의 선택을 D11 §4.1 이 *"이벤트 데이터 태그(스키마 D12)"* 로 확정했는데 **`vn_slots.csv`·`milestone_vn.csv` 어느 표에도 그 열이 없다.** 현행은 화면이 페이로드로 받고 미지정은 일상으로 둔다 — `vn_screen.gd:47~51` [가안] 계승분.

**신설안 문안 (그대로 승인/기각 대상)**

| 항목 | 안 |
|---|---|
| 열 이름 | `tone` |
| 대상 표 | `vn_slots.csv` · `milestone_vn.csv` (VN 발생 단위를 가진 두 표) |
| 값 도메인 | `calm` \| `tense` (표시 = 일상 / 긴장) |
| **미지정 기본값** | **`calm`(일상)** — 현행 [가안] 승계 |
| 기계 검증 | `config.json` 해당 표 `columns` 에 `"tone": "enum:calm,tense"` 추가 → V1 이 차단 |
| 소비 결선 | `vn_screen.gd` 의 `payload.get("tone", "calm")` 를 표 조회로 교체 · 발화 id = `vn_enter_calm` / `vn_enter_tense` (`sound_map.csv:78-79` — **이미 실재**) |

> **값 도메인이 코드 문자열과 일치해야 한다.** 표시 문면은 일상/긴장이지만 데이터 값은 `calm`/`tense` 다 — `sound_map` 의 event_id 가 그 문자열로 조립되기 때문이다.
> **D12 개정은 하지 않는다.** 본 신설안은 승인 대기 문안이며, T7 확정 시 총괄이 P-2 ㉛과 동시 집행한다(발주 §7.2-1 명문).

### 2.2 [집필] 채울 2행

대상은 **`pending_achievements()` 가 실측으로 세는 2건**이다(측정: `["achievement_relation_reunion", "achievement_relation_succession_maro"]`).

| 축 | 라이벌 | 필요한 `id` (업적이 지목하는 값 — **바꿀 수 없다**) |
|---|---|---|
| 재회 | **카이 셔우드** = `ai_sherwood` | **`relation_reunion`** |
| 계승 2축 | **셀린 마로** = `ai_maro` | **`relation_succession_maro`** |

> **id 는 집필 재량이 아니다.** `achievements.csv` 의 `source_id` 열이 이미 그 문자열을 가리키고 있고(`achievement_relation_reunion` → `relation_reunion`), 어긋나면 그 업적은 **영원히 pending 으로 남는다**(`_achievement_source_missing()`).

**납품 양식**

```csv
relation_reunion,ui.relation.<camelCase>,ai_sherwood,<counter_source>,<t1>,<t2>,<t3>
relation_succession_maro,ui.relation.<camelCase>,ai_maro,<counter_source>,<t1>,<t2>,<t3>
```

**동반 필수 — 스트링 키 2개.** `ui.relation.kinship/succession/throne` 은 실재하지만 **새 2축의 `name_key` 는 `strings.csv` 에 없다.** 행만 넣으면 **V2 가 빌드를 차단한다.** §3 대장에 함께 올린다.

### 2.3 ⚠ 이 행을 넣어도 카운터는 **자동으로 오르지 않는다**

실독 결과 두 가지를 보고한다.

1. **`counter_source` 를 읽는 코드가 없다.** 전 소스 검색 결과 이 열의 소비부는 0건 — 현재는 **문서용 표기**다. `adjacent_finish_and_duel` 같은 값은 사람이 읽는 메모이지 기계 계약이 아니다.
2. **`add_relation()` 의 production 호출이 0건이다.** 검사(`test_tc_o.gd`)만 부른다 — 즉 **기존 3축도 실주행에서는 오르지 않는다.**

> 따라서 관계 축 납품은 **행 + 트리거 규격**이 한 벌이다. 집필은 각 축에 대해 **"무엇이 일어나면 +1 인가"를 문장으로** 확정해 주면 되고(예: 기존 3축의 `counter_source` 문자열이 뜻하려 했던 것), **그것을 코드에 거는 것은 구현 몫**이다. 트리거 문장이 없으면 행은 들어가되 카운터는 0에 머문다.

**업적 2종의 판정 소스 요구 사항** — 두 업적 모두 `condition_type=reach` · `source=relation` · `threshold=3` 이다. 즉 **관계 단계 3(= `threshold3` 도달)이 달성 조건**이며, 축 행이 서고 카운터가 오르면 `evaluate_achievements()` 가 자동으로 켠다. 업적 표는 손대지 않는다.

## 3. 스트링 키 대장

### 3.5 V4 통과 조건 — 집필 산출물이 걸리는 지점

V4 는 **코드 안의 한글 리터럴**과 **표시 싱크에 닿는 비-키 문자열**을 차단한다. 집필 산출물이 `strings.csv` 로만 들어오면 V4 는 무관하다. **다만 문면 안에 매개가 있으면 `{name}` 형식을 쓴다** — 치환은 `StringTable.text()` 가 params 를 **삽입 순서대로 1회 훑으며** 하므로, 한 문면이 다른 키를 참조하고 그쪽에 또 매개가 있는 **중첩 구조는 쓰지 않는다**(중첩이 필요하면 [질문]으로 올린다).

### 4.2 [집필] CG-02 '대면' 도달 축 — 데이터 요구

CG-02 는 §2 의 `relation_reunion` 행이 서면 **한 갈래 추가로 닫힌다**(`race_screen.gd:1006` 주석의 "축이 들어오면 여기 한 갈래가 는다"). 필요한 것은 행 자체가 아니라 **'대면'이 몇 단계인가**다.

**[집필] 확정해야 할 1건**

| 항목 | 요구 |
|---|---|
| **'대면' = 관계 단계 몇?** | `relation_reunion` 의 **1 / 2 / 3 중 하나**로 지정. 이것이 `relation_stage("relation_reunion") >= N` 판정의 N 이 된다 |

**정본 참조 (집필의 출발점 — 이미 확정된 것)**
- D08 §8.7-3: *"재회 축 체인의 전개 규칙 (확정): 알타 리지 투어 내 브리핑·이벤트·벽 조우로 체인 1~2비트씩 전진, **'대면'은 체인 2~3비트째** (확정)"*
- D08 §8.7-2: 알타 리지는 매 시즌 투어 2~4 중 1회 등장 — **대면 도달 기회가 구조적으로 보장**된다
- D08 §8.7-4: 단서 2(사샤의 침묵)가 '대면' 도달을 **선행 조건**으로 가진다 → 사샤 영입 조건(D08 §8.6 단서 2 · §8.7 영입 구속)과 순서 결속
- D08 §8.7-1: 재회 축은 **형식 A — VN 발생(도달) 기준** 전이. 즉 카운터 +1 트리거 = **VN 발생**이며 열람 여부가 아니다(스킵해도 전이)

> **[질문 1]** 위 "체인 2~3비트째"가 `threshold1~3` 중 **어느 단계에 대응**하는가. 체인 비트 수와 관계 단계 수가 1:1이 아닐 수 있어 구현이 정하지 않는다.

### 4.3 CG-03 — **질문 목록 0건 (기판정·결선 완료)**

발주 §7.2-4 는 IMPL-126 을 근거로 CG-03 규격 부재 질문 목록을 요구했다. **실독 결과 그 전제는 이미 해소됐다** — 발주 근거가 낡았음을 보고한다.

집행분 = **IMPL-130**(`l3_kinship_for()` · `OutgameState.jude_overtaken` 래치 · `param_jude_adjacent_max` 데이터 전사). **집필이 답할 것이 없다.**

### 4.4 [질문] 잔여 3건

| # | 질문 | 왜 구현이 못 정하는가 |
|---|---|---|
| **1** | CG-02 '대면' = 관계 단계 1/2/3 중 어느 것 (§4.2) | D08 은 "체인 2~3비트째"라 하고 관계 단계와의 대응은 침묵 |
| **2** | 관계 축 2종의 **카운터 +1 트리거** (§2.3) | 재회는 형식 A(VN 발생)가 확정이나 **계승 2축(마로)은 형식이 미규정**. 기존 3축조차 소비부가 없어 준거로 삼을 실물이 없다 |
| **3** | **막(`act`) 전이 규격** | DSL 문맥의 `act` 가 **1 고정 [가안]**이다(`run_session.gd:90`). 막 전이는 마일스톤 래치 층(D08 §8.1 서사 층) 소관이며 미결선 — 4막 문안이 `act` 조건을 쓰려면 전이 규격이 선행해야 한다 |

> **CG 도트 실물(CG-01~03)은 별건이다** — 조건은 서 있고 **컷인 재생 소비부가 미결선**이다(T6 · D10 §6.2). 본 계약의 범위 밖이며 집필 대기 항목이 아니다.
