## 0. 진행 원칙

1. **선행 문서 우선:** 각 문서는 의존하는 선행 문서가 확정된 후 착수한다.
2. **확정 후 기록:** 모호한 사항은 임의로 결정하지 않고, 채팅으로 사용자와 합의하여 확정된 내용만 문서화한다.
3. **완결성:** 최종 산출물 전체를 합치면 기획·아트·사운드·기술·데이터·QA까지 게임 제작에 필요한 모든 정보가 담겨야 한다.
4. **소규모 팀 전제:** 역기획 4단계에서 확정한 제약(저비용 연출, 턴제 상태 머신, 데이터 드리븐)을 모든 문서가 준수한다.
5. **원 코어, 투 플랫폼:** 코어 메카닉·시스템·데이터는 플랫폼 공통으로 단일 설계하고, UI/UX와 수익 모델 레이어만 플랫폼별로 분리한다. 시스템 문서(D05~D08)에 특정 플랫폼 전용 규칙이 섞이지 않도록 한다.

## 0.5 표준 작업 프로세스 (문서별 제작 사이클) — 확정

모든 문서(D01~D16)는 아래 5단계 사이클로 제작한다. 이 프로세스는 프로젝트 전체에 걸쳐 유지한다.

| 단계 | 주체 | 내용 |
|------|------|------|
| **① DoD 정의** | 에이전트 → 사용자 승인 | 해당 문서가 '실제 게임 제작에 투입 가능'하기 위한 세부 완료요건(Definition of Done) 체크리스트를 에이전트가 작성하여 제시. 사용자가 항목을 가감·승인. |
| **② 핵심 결정** | 에이전트 제안 → 사용자 확정 | 문서의 방향을 가르는 핵심 결정 항목만 추려, 각 항목당 **선택지 2~3개 + 추천안 + 근거**를 제시. 사용자는 선택 또는 수정 지시. (열린 질문 최소화) |
| **③ 초안 작성 (Draft-first)** | 에이전트 | 확정된 핵심 결정을 반영하고, 미확정 세부 항목은 에이전트 추천값을 **[가안]** 태그로 채워 넣은 '완성형 초안 v0.1'을 작성. 사용자는 빈칸에 답하는 대신 채워진 초안을 교정한다. |
| **④ 피드백 루프** | 사용자 ↔ 에이전트 | 피드백 반영 시마다 v0.x 버전 증가. 확정된 의사결정은 문서 하단 **결정 로그(Decision Log)**에 사유와 함께 누적 기록하여 재논의를 방지. |
| **⑤ 확정** | 사용자 | DoD 체크리스트 전 항목 통과 확인 후 **v1.0 확정**. 본 로드맵의 상태를 ✅로 갱신. 확정 문서는 프로젝트 지식베이스에 업로드하여 다음 문서의 입력으로 삼는다. **확정 전 전수 리뷰에는 의존 거리와 무관하게 'D01 보장 조항 대조'를 고정 항목으로 포함한다(v2.11 신설 — D07 제안 채택):** D01의 G1~G4류 보장 조항(첫 소구 원칙·내러티브 비강제성·접근성 등 *플레이어에 대한 약속*)은 직접 의존 문서가 아니어도 모든 문서가 위반할 수 있다. *신설 사유: D07 v1.0의 정합 리뷰가 직접 의존(D06)·이관 출처(D03~D06) 중심으로 수행되어 의존 거리가 먼 D01 §4 G2 조건 2를 누락, VN 회상이 유상 게이트 뒤에 놓이는 취지 역전이 확정 후에야 발견되었다(R-D07-VN).* |

**공통 규칙**
- 버전 표기: 초안 v0.1 → 피드백 반영 v0.2, v0.3… → 확정 v1.0 (확정 후 수정 발생 시 v1.1…, 로드맵 상태는 🔁로 변경 후 재확정)
- [가안] 태그는 v1.0 확정 시점에 모두 해소(확정 또는 삭제)되어 있어야 한다.
- 모호한 사항의 임의 확정 금지. 단, [가안] 형태의 '추천값 제시'는 적극 권장.

## 0.6 채팅 운영 규칙 (Chat Operation Protocol) — 확정

연속성의 원천은 채팅 이력이 아니라 **확정 문서(지식베이스)**에 둔다. 컨텍스트 한계로 인한 품질 저하와 강제 단절을 예방하기 위해 아래 규칙을 따른다.

1. **채팅 단위 = 문서 1개.** D01~D16 각 문서는 전용 채팅에서 제작한다. (Phase 단위 통합 금지 — 특히 D02, D05는 단독으로도 피드백 루프가 깊음)
2. **채팅 시작 규칙:** 새 채팅 첫 메시지는 "D0X 시작"이면 충분하다. 에이전트는 다음의 **시작 체크리스트**를 수행한 후 ① DoD 정의부터 착수한다:
   - 지식베이스에서 본 마스터플랜의 최신 버전과 대상 문서의 상태를 확인
   - 의존성 표 기준 **선행 문서의 v1.0 이상의 확정본이 지식베이스에 존재하는지 검증** (누락 시 작업을 시작하지 않고 사용자에게 보고)
   - 선행 확정 문서의 결정 로그와 용어집을 숙지
3. **채팅 종료 조건:** 해당 문서 v1.0 확정 → 에이전트가 마스터플랜 상태표 갱신본(✅)을 함께 산출 → 사용자가 확정 문서와 갱신된 마스터플랜을 지식베이스에 교체 업로드 → 채팅 종료.
4. **긴 루프 예외:** 한 문서의 피드백 루프가 길어져 채팅이 무거워지면, 최신 v0.x 파일을 지식베이스에 임시 업로드하고 새 채팅에서 이어간다(문서가 원천이므로 손실 없음). 임시 업로드본은 v1.0 확정 시 교체한다.
5. **총괄 채팅:** '로드맵 수립' 채팅은 종료 후 **총괄/서포트 채팅**으로 전환·유지한다. 역할: 로드맵 자체의 수정, Phase 간 연결 점검, 문서 간 충돌 중재, 진행 상황 리뷰. 개별 문서의 상세 제작은 총괄 채팅에서 수행하지 않는다.

## 0.7 공통 작성 규칙 (Cross-Document Standards) — 확정

여러 채팅에 분산 작업되어도 통일성을 유지하기 위한 횡단 규칙.

1. **파일 네이밍 (v2.8 확정 / v2.9 재확인 — 예외 없음):** ⟨**본 항이 파일명 표기의 유일한 현행 근거다.** 갱신 이력·판정 요지·원장에 남은 과거 규칙 서술은 모두 폐지분이며 인용 금지⟩ **확장자 앞의 마침표 하나를 제외하고, 파일명의 모든 구분자·공백은 언더스코어(`_`)를 쓴다.** 판번도 예외가 아니다.
   - 형식: `D0X_문서명_v0_x.md` — 예: `D01_게임컨셉_v1_0.md`, `D02_세계관설정집_v1_8.md`, `master_plan_v2_8.md`
   - **금지:** 확장자 외 위치의 마침표(`v1.0`), 공백, 하이픈. 마침표·언더스코어 병용도 금지한다.
   - **유니코드 NFC 정규형**으로 저장한다 (§0.8.7).
   - 지식베이스에는 문서당 최신 1개 버전만 유지한다. 판번 표기가 구 규칙인 파일은 다음 내용 갱신 시점에 함께 교정한다(파일명 교정만을 위한 재업로드는 불요).
   - **본문 내 판번 서술은 마침표를 유지한다** (`v1.0 확정`, `D05 v1.1 참조`). 본 항의 언더스코어 규칙은 **파일명에만** 적용되며, 산문·표·결정 로그의 판번 표기와는 층위가 다르다.
   - *(개정 경위: v1.6~v2.6은 '판번은 마침표'를 유일 기준으로 삼았으나, 확장자 외 위치의 마침표가 저장 시 언더스코어로 자동 변환됨이 실증 확인되었다. v2.6은 이를 '병용 허용'으로 흡수했다가 표기 혼선을 낳았고, v2.7은 마침표 단일 기준으로 되돌렸으나 실태와 계속 어긋났다. v2.8은 **규칙을 실태에 맞추는 방향**으로 최종 정리하여, 발행·저장·표시의 세 층위가 항상 동일한 문자열을 갖도록 한다.)*
2. **단일 용어 기준 (Glossary):** D02 세계관 설정집에 **용어집**을 두고, 모든 고유명사(대회명, 머신, 재화, 자원, 시스템 명칭)는 용어집 표기를 유일한 기준으로 삼는다. 후속 문서에서 신규 용어가 확정되면 D02 용어집에 추가하는 것을 해당 문서의 DoD에 포함한다.
3. **문서 간 충돌 처리:** 후속 문서 작업 중 선행 확정 문서와 모순이 발견되면, **임의로 어느 쪽도 수정하지 않는다.** 충돌 내용·영향 범위·해결 선택지를 사용자에게 보고하고, 선행 문서 수정으로 결정되면 해당 문서를 🔁 상태로 전환 후 재확정한다.
4. **문서 공통 구조:** 모든 문서는 ①문서 목적·범위 ②본문 ③미결 사항(있을 경우) ④결정 로그 ⑤DoD 체크리스트(확정 시 전항목 체크) 순의 골격을 갖춘다.
5. **참조 표기:** 다른 문서의 내용을 인용할 때는 문서 번호와 절 번호로 표기한다(예: "D05 §3.2 참조"). 내용을 복제하지 않아 이중 관리와 버전 불일치를 방지한다.
6. **역기획 문서(1~4단계)의 지위:** 역기획 산출물은 '분석 자료'로서 참조하되, D01 이후 확정 문서와 충돌 시 **확정 문서가 항상 우선**한다.
7. **식별자 네임스페이스 (v2.24 신설 — D13 v1.3 회부):** 문서 간 통용 식별자와 문서 내부 식별자의 충돌을 방지한다.
   - **신규 식별자는 반드시 2문자 이상 접두 + 하이픈**을 쓴다 (`RG-1`, `C-A1`, `R-D07-2`, `G-M2`, `P-5` 등). **무접두 단문자+숫자 형태(`G1`, `T1`, `V1` 등)의 신규 도입을 금지한다.**
   - **기존 무접두 식별자는 개명하지 않는다** — 상류 확정 문서가 소유하며 파급이 과대하기 때문이다. 다만 **인용 시 출처를 반드시 병기**한다: "D01 §4 **G2**", "D07 시설 **G3**", "D06 §7 **G1**".
   - *신설 사유 (총괄 전수 조사, 2026-08-06):* 무접두 `Gn`이 **5계통**을 지칭하고 있다 — ①**D01 §4 보장 조항** G1·G2(거의 전 문서가 인용) ②**D06 §7 환전 가드** G1~G4 ③**D07 개러지 시설 ID** G1~G4 ④**D08 DoD 그룹** G1~G3 ⑤**D11 DoD 그룹** G3·G4. 특히 **D09·D09-2 내부에서 D01 보장 G1과 D07 시설 G1이 동일 표기로 병존**한다. 하이픈 접두형(`G-1` D12 검증 게이트 vs `G-1` D13 범위 가드)의 충돌은 D13 v1.3 `RG-n` 재명명으로 해소했으나, **접두 분리만으로는 무접두 충돌이 남는다**는 D13의 지적에 따라 인용 규칙으로 통제한다.
   - **D14·D15 착수 시 본 항을 DoD에 승계**하며, 신규 식별자 도입 시 기존 5계통과의 충돌 여부를 검사한다.

## 0.8 총괄 운영 규정 (Supervisory Chat Charter) — 확정

> **신설 사유 (v2.4):** 총괄 채팅의 판정 관행이 채팅 기억에만 존재하여, 0.6절의 원칙("연속성의 원천은 문서")이 정작 총괄 자신에게는 적용되지 않는 공백이 있었다. 본 절은 그 관행을 규정화하여 **총괄 채팅의 교체를 안전하게** 만든다. 신임 총괄 채팅은 시작 시 본 절과 §4.5를 필수로 숙지한다.

### 0.8.1 총괄 채팅의 권한과 금지

- **권한:** ①마스터플랜 자체의 개정 ②문서 간 충돌·개정 요청의 중재 판정 ③확정 문서에 대한 **사전 예약 수정의 집행**(0.8.4) ④Phase 완결 교차 검토 ⑤Phase 간 연결 점검·진행 리뷰.
- **금지:** 개별 문서의 상세 제작(0.6-5 재확인). 사전 예약되지 않은 확정 문서의 내용 변경 — 이 경우 반드시 사용자 승인을 선행한다.
- **원칙:** 총괄은 문서를 기억하지 않고 **매 건 파일에서 상태를 다시 읽는다.** 채팅 기억을 판정 근거로 삼지 않는다.

### 0.8.2 중재 판정 5단계 절차 (필수)

문서 채팅이 개정 요청·충돌 보고를 발신하면 아래 순서를 지킨다. 단계 생략 금지.

| 단계 | 내용 |
|---|---|
| ① 접수·성격 판별 | 요청이 (a)사전 예약 수정 (b)신규 개정 (c)충돌 중재 중 무엇인지 판별. 예약 조건이 소멸했는데 신규 요건이 붙어 온 경우 **'신규 안건으로 전환'을 명시**한다. |
| ② 원문 대조 검증 | 지식베이스의 **해당 문서 원문을 직접 열어** 현행 문구·보고 내용의 일치를 확인. 요청문만 근거로 판정하지 않는다. |
| ③ 파급 전수 조사 | 요청 대상 절뿐 아니라 **동일 문구가 등장하는 모든 절·타 문서·용어집·마스터플랜 §4 이관 문구**를 조사. *요청자가 누락한 파급을 총괄이 추가 발견한 전례 2건(D02 §7 파급, 마스터플랜 §4 이관 문구 모순) — 이 단계가 총괄의 핵심 기여다.* **③-b 마스터플랜 자기 파급 조사 (v2.9 신설·필수):** 개정 대상이 **마스터플랜 자신의 규칙(§0.5~§0.8)**일 때는, 마스터플랜 **전문을 대상으로 구 규칙 문자열을 역검색**하여 ⓐ다른 절의 **살아 있는 지시문**에 구 규칙이 박혀 있지 않은지 ⓑ§4·§4.5의 이관 문구·원장 항목이 구 규칙을 전제하지 않는지 확인한다. 갱신 이력·판정 요지처럼 **보존이 목적인 과거 기록**은 수정하지 않되 `[폐지]`를 부기한다. *신설 사유: §0.7-1을 v2.6→v2.7→v2.8로 세 차례 개정하면서 §4.5의 NFD 운영 규칙 항목에 박힌 "마침표 표기 교정" 지시문을 매번 놓쳤고, 그 결과 규칙과 정면 모순되는 지시가 3개 판에 걸쳐 존속했다. 규칙 개정 시 정작 마스터플랜 자신은 파급 조사 대상에서 빠져 있었던 것이 근본 원인이다.* |
| ④ 판정·부대조건 | 승인/반려/조건부 승인. 승인 시 파급 차단을 위한 **부대조건**을 부과할 수 있다(예: "신규 아트 0", "실배치는 D08 이관"). 부대조건은 대상 문서 본문에 명문화시킨다. |
| ⑤ 발행·회신 | 관련 문서 전부의 갱신본을 일괄 산출 + **발신 채팅용 회신문**을 동봉(조치 사항·종결 처리 지시 포함). 업로드 대상 파일명을 명시한다. |

### 0.8.3 판정 층위 기준 (D02 본문 변경 여부의 판단)

개정 요청을 아래 층위로 분류하여, 상위 층위일수록 신중히 판정한다.

| 층위 | 성격 | 처리 |
|---|---|---|
| L-A 세계관 설정 변경 | 설정 자체가 달라짐 | 사용자 승인 필수 + D02 본문 개정 + 🔁 경유 후 재확정 검토 |
| L-B 역할·연출 배분 조정 | 설정은 불변, 담당·표현만 재배치 (예: 화자 재배분) | 사용자 승인 필수. D02 본문의 해당 문구만 교체, DoD 재심사 불요 |
| L-C 용어 등재·정의 부기 | 정의 본문 불변, 항목 추가·상태 갱신 | 사전 예약 수정으로 처리(0.8.4) |

### 0.8.4 사전 예약 수정 처리 규칙

확정 문서의 갱신 중, **선행 확정 시점에 이미 예약되어 있던 수정**(용어집 등재, [가안]의 이관처 해소, 미결 항목의 예정된 종결)은 다음과 같이 처리한다. 전례 6회(D02 v1.1~v1.6) 적용.

- 🔁(수정 필요) 상태를 **경유하지 않는다.** ✅ 확정 상태를 유지하며 버전만 증가(v1.x).
- 헤더 상태란에 "사전 예약 수정 집행 / 설정 변경 없음"을 명기하고, **결정 로그에 집행 근거를 기록**한다.
- DoD 재심사 불요. 단, DoD 체크리스트의 해당 항목 서술은 실태에 맞게 갱신한다.
- **중복 집행 방지:** 집행 전 대상 문서의 결정 로그를 확인하여 기집행 여부를 확인한다. *전례: D05가 요청한 '더블 챔피언' 갱신이 직전 중재의 D02 v1.5에서 기집행되어 중복 제외된 건.*

### 0.8.5 Phase별 총괄 채팅 배정 (확정)

컨텍스트 신선도를 유지하기 위해 총괄 채팅도 Phase 단위로 교체한다. Phase 2는 문서 수가 타 Phase의 2배이므로 내부 분할한다.

| 총괄 채팅 | 담당 문서 | 마지막 임무 | 상태 |
|---|---|---|---|
| **Phase 1 총괄** (구 '로드맵 수립') | D01~D05 | §0.8 신설·인수인계 | ✅ 종료 (2026-07-22) |
| **Phase 2-A 총괄** | D06, D07, D08 | Phase 2-B로 인수인계 | ✅ 종료 (2026-07-30) |
| **Phase 2-B 총괄** | D09, D16, D09-2 | **Phase 2 완결 교차 검토** | ✅ **종료 (2026-08-02)** — 담당 전량 확정(D09 v1.1·D16 v1.0·D09-2 v1.0), 교차 검토 통과 13·경미 2(P-2 이월)·공백 0·충돌 0 |
| **Phase 3 총괄** | D10~D13 | Phase 3 완결 교차 검토 | ✅ **종료 (2026-08-08)** — D10 v1.0·D11 v1.0·D12 v1.0·D13 v1.3 확정 + 완결 교차 검토 종료(통과 13·경미 4·공백 1·충돌 0 — 전건 해소). 인계 완료(v2.25) |
| **Phase 4 총괄** | D14, D15 | **최종 전체 검토(D01~D16)** | ✅ **임무 완료 (2026-08-09)** — D14 v1.0·D15 v1.0 확정 + **최종 전체 검토 종료(통과 11축·경미 4·공백 0·충돌 0 — 전건 처리)**. **파이프라인 D01~D16 완결.** 이후 = 실행 단계 존속 트랙(P-2 잔여 12·P-4·P-6·P-7·게이트 실측·조건부 발신 — **전건 총괄 경유 규정 존속**) 대응, 사용자 지시로 재개. **재개 이력: 2026-08-11 D12 v1.1 사후 동기(v2.29)** |

- 동시에 활성화되는 총괄 채팅은 **1개**로 한다(판정 주체의 단일성 보장).
- 담당 범위를 벗어난 문서의 사후 개정 요청(예: Phase 3 진행 중 D02 개정)도 **현재 활성 총괄이 처리**한다. 범위는 진행 시점 기준이며 문서 소유권이 아니다.

### 0.8.6 총괄 채팅 시작·종료 규칙
- **시작:** 첫 메시지는 "Phase N 총괄 시작"으로 한다. 신임 총괄은 ①마스터플랜 최신본의 §0.8·§4.5 숙지 ②지식베이스의 확정 문서 목록·버전 대조 ③§4.5의 인수 안건 확인을 수행한 후 대기 상태로 들어간다. **선제적으로 문서 제작을 시작하지 않는다.**
- **종료:** 담당 Phase의 문서가 전부 ✅ 확정되면 ①마지막 임무(교차 검토) 수행 ②잔여·조건부 예약 안건을 §4.5에 이기 ③마스터플랜 갱신본 발행 ④인수인계 요약문 산출 후 종료.
- **Phase 완결 교차 검토 (의무):** 담당 Phase 문서 전체를 상호 대조하여 수치 모순·범위 공백·용어 불일치·이관 누락을 점검하고, 발견 사항을 마스터플랜에 반영한다. *전례: Phase 1 착수기의 총괄 리뷰 1차(5건 발견 — 산술 모순, 로컬라이제이션 공백, 접근성, 범위 가드, 파일 네이밍)와 동일 성격의 정규 절차다.*
- **종료된 총괄 채팅의 취급 (v2.9 신설):** 종료된 총괄은 **종료 시점의 스냅숏 상태**를 보유할 뿐 이후 판의 규칙 개정을 알지 못한다. 따라서 ①**규칙·판번·확정 상태에 관한 판단 근거로 삼지 않는다** — 이런 질의는 활성 총괄 소관이다 ②반면 **파일 판독 가능 여부, 렌더링 확인처럼 시점에 의존하지 않는 경험적 점검**에는 활용해도 무방하다 ③종료 총괄이 규칙 관련 의견을 낸 경우, 활성 총괄은 이를 **의견이 아니라 신호로 취급**한다 — 결론이 틀렸더라도 그렇게 읽히게 만든 모순이 문서에 실재하는지 확인한다. *전례: 2026-07-26 Phase 1 총괄이 "§0.7-1은 마침표 기준"이라 지적했고 결론은 사실과 달랐으나(v2.8에서 이미 언더스코어 확정), §4.5에 구 규칙 지시문이 살아 있던 실제 결함을 드러냈다(v2.9 §4.5 교정).*

### 0.8.7 파일 발행 위생

- 파일명은 0.7-1을 따르고, **유니코드 NFC 표준형**을 사용한다(NFD 자모 분해형은 도구가 인식하지 못할 수 있음).
- **판번 일관성 검사 (v2.8 신설 — 발행 전 필수):** 문서를 발행하기 전, 판번이 등장하는 **모든 지점**을 목표 판번과 대조한다. 최소 검사 지점은 ①**제목행** ②**헤더 상태란**(판올림 사유 기재 여부) ③**갱신 이력 선두** ④**DoD 체크리스트 헤더** ⑤**파일명** ⑥**의존 문서 행 — 해당 판의 *발행 시점* 기준 확정 판번과 동기**(v2.18 신설 — Phase 2 교차 검토 F-2: D09 v1.1이 재발행 시점의 D01 v1.2·D02 v1.11 대신 구판을 표기)⑦**마스터플랜 §1 상태표 행 — 각 문서의 확정 판번 동기**(v2.22 신설 — D13 v1.0 발신 O-1 지적: §1 상태표의 D01이 `v1.0`·D02가 `v1.10`으로 잔존. 종전 규정이 *발행 대상 문서*만 검사 대상으로 삼아 **마스터플랜 자신의 상태표가 공백**이었다. 마스터플랜 발행 시 §1 전 행을 실제 확정본과 기계 대조한다 — §0.8.2-③b 자기 파급 원칙의 이행)이며, 하나라도 어긋나면 발행하지 않는다. *신설 사유: v2.7 발행본이 제목행 v2.6 / 갱신이력 v2.7 / 파일명 v2_7의 3중 불일치 상태로 나갔고, 이를 총괄이 아니라 **발신 채팅(D06)이 발견**했다. 판번 갱신 지점이 문서 내에 분산되어 있어 수동 처리 시 누락이 반복되므로, 육안 확인이 아니라 **기계적 전수 대조**를 절차로 못박는다.*
- 문서 갱신은 **최신 확정본을 복제한 뒤 구간 치환**하는 방식으로 수행한다(전문 재작성 금지 — 의도치 않은 내용 유실 방지).
- 발행 시 업로드 대상(교체 전/후 파일명)을 사용자에게 명시한다. 총괄이 발행한 버전과 지식베이스 버전이 어긋난 경우 **버전 주석으로 경위를 남긴다.**
- 지식베이스에서 파일이 보이지 않을 때는 **부재로 단정하지 않는다** — 파일명 인코딩·표기 차이일 수 있으므로 사용자에게 확인을 요청한다. *전례: v2.2의 오탐 경보.*

- **검사의 기계화 (v2.24 강화 — 총괄 자기 시정):** 위 7지점은 **전량을 기계 대조**하며 일부라도 육안 확인으로 대체하지 않는다. *신설 사유: v2.22·v2.23 배치에서 총괄이 D13 v1.1·v1.2를 발행하며 **④DoD 체크리스트 헤더를 2회 연속 미동기**(v1.0 잔존)했고, 이를 총괄이 아니라 **발신 채팅(D13)이 발견**했다. 규정 자체는 v2.8부터 있었으나 총괄의 발행 전 검사가 제목행·파일명·상태표 등 일부만 스크립트로 대조하고 나머지를 육안 처리한 것이 원인이다. 지점을 늘리는 것으로는 재발을 막지 못하며, **전 지점 기계 대조를 절차로 못박는다.***

## 3. 순서 설계의 근거

- **세계관(Phase 1)을 시스템(Phase 2)보다 먼저** 두는 이유: 본 게임은 '내러티브 기반'이 정체성이므로, 스핀 심볼·자원·이벤트의 이름과 규칙이 모두 레이싱 세계관 언어로 정의되어야 함. (예: '스핀'이 레이싱 세계에서 무엇을 의미하는지 D02~D04에서 먼저 답해야 D05가 겉돌지 않음)
- **경제(D06)를 아웃게임(D07)보다 먼저** 두는 이유: 재화의 소모처(Sink)가 겹치지 않게 하려면, 재화 구조가 먼저 확정된 뒤 상점·튜닝 등의 소모처를 배치해야 함 (역기획 2.5단계 원칙).
- **UI/UX(D09)를 Phase 2 마지막**에 두는 이유: 모든 시스템이 확정되어야 화면 플로우와 레이아웃의 누락이 없음. 데스크탑(D09)을 먼저 확정하고, 모바일(D09-2)은 이를 세로 모드로 재구성하며 광고 UX를 얹는 순서로 진행함.
- **BM 문서(D16)를 D09-2 이전**에 두는 이유: 모바일 광고의 유형·노출 지점·보상 규칙이 확정되어야 모바일 화면에 광고 UX를 배치할 수 있음. 또한 광고 보상이 인게임 경제(D06)를 붕괴시키지 않도록 경제 설계와 교차 검증이 필요함.
- **데이터 테이블(D13)을 기술설계(D12) 이후**에 두는 이유: 스키마가 아키텍처(데이터 드리븐 구조)와 일치해야 함.

> **판정 요지 (§0.8.2 ③ 파급 전수 조사 — 총괄 추가 발견 3건):** ①**'주행 데이터'의 기사용** — D02 **§3.2**(관제 시스템 설명)·D03 §1.1(마르타의 발탁 경위)에서 이미 **일반 서술어**로 사용 중 *(v2.7 정정 — v2.6 원문은 §4로 오기. §4에 있는 것은 '주행 변수')*이며 D06 발신문은 이를 누락. 재화명은 UI 상시 노출로 심볼명보다 노출 빈도가 높고, UI 약칭 '데이터'는 악시온의 **'데이터 지상주의'**(D02 §5.1·§8, D03 §2.2, D04 §6)와 의미 간섭 가능. 다만 반려 사유는 아니며 — 오히려 데이터를 신봉하는 악시온과 자기 주행 기록을 자산화하는 플레이어의 대비는 D04 기원 서사와 정합 — **'브레이킹 포인트' 항목의 병존 전례(D02 v1.4)를 준용**하여 부대조건 **B-1**(병존 조항 부기 + UI 약칭의 아이콘 동반 표기 필수, D09·D12 이행)으로 해소. ②**'시즌 오버홀' 상태 열** — 현행이 `확정(명칭)`인데 D06 §5.3이 구조를 확정하여 명칭 한정 유보 사유가 소멸했음에도 D06 제안 문구는 정의만 갱신하고 상태를 누락 → 총괄이 `확정`으로 승격. ③**파일 위생 실태** — 지식베이스 표시명에서 마침표가 언더스코어로 바뀌는 현상을 2회 관측(내용 무손실). *(v2.7 정정: v2.6은 이를 근거로 §0.7-1에 병용 허용을 넣었으나, 예외가 표기 혼선을 낳아 **철회**했다. 규칙은 마침표 단일 기준이며, 변환 관측은 아래 운영 기록으로만 존치한다.)* **[폐지 — v2.8에서 전면 언더스코어로 재개정. 현행 규칙은 §0.7-1을 볼 것]** 부대조건 **B-2**: '벽(Wall)'은 D02 §8 미등재 난이도 용어이므로 §5.1 본문을 **개정하지 않고 존치**한다(L-A 회피 — 표기 정리는 마스터플랜 층위로 한정).

> **자기 점검 (§0.8.2 ② 원문 대조 검증의 실패 사례):** 본 건은 총괄이 파급 조사에서 **문자열 검색 결과의 행 번호만 보고 소속 절을 확인하지 않아** 발생한 인용 오류다. 발신 채팅이 이를 역검증하여 지적했다 — ②단계가 발신 측에서도 작동한 유효 사례이며, 총괄 판정이라 하여 무조건 수용되지 않는다는 점에서 절차가 건강하게 기능했다. **재발 방지:** 파급 조사에서 절 번호를 인용할 때는 문자열 히트의 **소속 절을 역산하여 명시**한다(행 번호 → 최근접 상위 헤더 매핑).

> **자기 점검 2 (§0.8.7 발행 위생의 실패 사례 — 동일 상대에게 2회 연속):** v2.7 발행본의 **제목행 미갱신**(제목 v2.6 / 갱신이력 v2.7 / 파일명 v2_7의 3중 불일치)을 역시 **D06 채팅이 발견**했다. 총괄의 발행 위생 오류가 연속 2회, 모두 발신 채팅에 의해 검출된 것은 **총괄의 자체 검증 절차가 육안 확인에 의존**하고 있었기 때문이다. **재발 방지:** §0.8.7에 판번 일관성 전수 대조를 의무화하고, 검사 지점을 5종(제목행·헤더 상태란·갱신 이력 선두·DoD 헤더·파일명)으로 명시했다. 이후 총괄은 발행 전 이 대조를 기계적으로 수행한다.
